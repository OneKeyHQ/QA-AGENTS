# 覆盖审计、发布风险与测试工作量

适用：所有 PR 最少记录覆盖缺口，完整/深度模式或用户要求时交付详细覆盖、发布建议及工时。不得用代码行数、自动化通过数量或模拟通过直接推断发布安全。

默认快速首轮用简短清单记录本轮已验入口、状态、平台和缺口，按主技能第 3.2 节交付。完整覆盖细表、发布评估及工时估算在完整/深度模式或用户明确要求时提供。涉及资金、权限、包或 OTA 的验证边界在首轮也须说明，相应结论依实际证据判定。

## 1. 建立可审计的覆盖集合

先枚举本次范围、记录各项唯一标识和预期，再标记实际完成状态。覆盖集合应来自实际文件清单、需求和调用链，不虚构分母。没有完整清单时只写已核实数量与未知范围。

| 维度 | 分母 | 分子/状态口径 |
| --- | --- | --- |
| 需求 | 已读取并拆分的适用验收点数 | 按静态符合/不符、隔离执行、真实环境及未验证分别统计；不适用另列 |
| Diff/变更文件 | 实际完整变更文件清单 | 已审查、未审查、不适用（原因）；生成产物/二进制也要记账 |
| 关键逻辑 | 已识别的适用关键分支/调用链/状态转换 | 已静态核实、实际测试、失败、未执行 |
| 异常 | 已计划的适用异常/状态组合 | 实际执行、通过、失败、阻塞、未执行 |
| 平台 | 真实受影响的平台/独立布局分支 | 分列实际入口运行、原组件隔离、源码重建与未运行。原生平台需标明实际运行环境 |
| 资金生命周期 | 实际适用的阶段 | 已捕获或核对的阶段；未执行/不适用阶段单列 |
| i18n | 实际引用 key 与已支持 locale 的适用组合 | 字典/ICU 核对、真实文案、局部渲染、真实端结果分别统计 |

只在分母明确、分子同口径时报告比例。静态审查覆盖、验收覆盖、脚本断言覆盖和仪器采集的语句/分支覆盖率不同；无覆盖工具输出时不要使用“代码覆盖率 XX%”。不同层级可能重叠，不直接相加。对相关实验报告真实执行结果（通过/失败/阻塞/未执行），不能用预览状态生成虚假通过数。

按验收点和平台分别关联固定源码、回归项、运行入口、观测与结论。同一真实组件独立挂载时，只统计已执行的组件行为。只有从产品入口运行，且影响该点的父路由、容器状态与门禁均生效，才计入实际页面路径。重建页的浏览器检查可报告演示结果，原平台相应验收点单列待验。经调用链确认没有界面影响时，记录文档、配置或逻辑检查。详细表可留本地临时报告。

## 2. 包、OTA、平台与发布检查

- 核对真实提测包的版本、branch/commit、bundle 编号及构建来源；PR head、最新 x、真实已安装包和临时合并树不能混为一个版本。
- 涉及 native module、patch、registry、依赖/构建配置、懒加载或桥接时，核对实际 app 原生版本、OTA Bundle 兼容关系、必需的安装包/热更新路径、冷启动/升级/解锁与失败回退；旧包能否加载新 bundle 按项目真实契约验证。未验证安装包时不宣称兼容。
- 核实目标 SHA 的 CI/check 状态、开发自测范围及尚未验证端；CI 绿不替代实机和关键业务验证。系统升级、设备及原生手势等仅在真实授权环境测得才算真实通过。
- 记录测试环境、账号、测试数据、设备、包、服务端配置及等待修复等外部依赖。只有可达具体证据才能报缺陷；覆盖缺口本身是风险/阻塞而非 bug。

## 3. QA 发布建议（非发布审批）

| 建议 | 适用条件 |
| --- | --- |
| 建议进入正常测试 | 已审范围没有明确阻塞缺陷，关键验证有可执行方案；不等于可以发布 |
| 需重点专项测试 | 高风险改动、跨模块/平台、重要验证缺口或待确认的具体风险 |
| 建议修复后再验收 | 已确认关键操作/资产/状态异常，影响当前验收 |
| 建议阻塞发布 | 有可达证据的资金安全/越权或重大核心功能阻断；或关键发布门禁缺失使发布安全无法确认（明确这是验证阻塞，不冒充已确认 bug） |

依据 QA-AGENTS 现行发布/严重程度规则；说明判断依据、待解决事项、最小复核条件。没有发布权限不代用户发布/拒绝 PR。未拿完整 diff 时明确“审查未完成”，不得以“未发现问题”暗示安全。

## 4. 工时估算与排期

以具体模块、复杂业务场景数量、共享组件、独立平台分支、设备/数据准备、真实签名/链上等待、异常复测、语言与主题、发布包/OTA、修复回归为输入，不用 LOC 直接换算。使用团队既有测量或明确假设（如每天有效测试 6~8 小时，按用户实际工作方式调整）。

- 分开估首轮验收、直接/间接回归、专项（资金/兼容/i18n/性能）、一轮修复验证；给区间及最关键的耗时项。
- 检查分项低/高值和总计一致，说明是否含修复复测。QA 人日和自然工作日分开，2/3 人并行按关键路径、设备依赖、接口联调和协调开销估，不简单按人数除法。
- 开发修复等待、包未出、活动/链上结算、外部资源阻塞单列，不计入纯 QA 执行人日；如影响日历周期则说明。
- 建议负责人按模块/平台拆分，避免两人重复跑同一等价路径；共享核心风险需要交叉验证时明确原因。估算不是承诺，需求、缺陷数量及修复轮次变化时应重新评估。
