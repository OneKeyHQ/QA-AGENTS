# Hardware - 蓝牙与USB交互中断

> 规则文档：docs/qa/rules/hardware-rules.md（§19）
> 需求文档：docs/qa/requirements/Hardware-通用专项用例补齐.md
> 测试端：iOS / Android / Desktop / Extension / Web（按本份适用通道及第三方钱包范围执行）
> Jira 对应：OK-24216；仅同步description，保留未授权修改的字段。

## 前置条件

1. 适用设备：Classic / Classic 1S / Classic Pure（Pure）/ Touch / Pro / Pro2 / Neo；Mini 不支持蓝牙，不执行蓝牙部分。
2. 准备手机蓝牙与Desktop USB，设备已激活；分别准备可区分的地址核对A与待签名交易B。
3. Pro2保留蓝牙不能打断USB的差异；中断前均不确认交易，不将已广播交易作为中断样本。

## 1. 用例内容

| 优先级 | 场景 | 操作步骤 | 预期结果 |
| --- | --- | --- | --- |
| ❗️❗️P0❗️❗️ | USB打断蓝牙待签名交易 | 蓝牙进入交易B确认页，随后从USB发起地址核对A | 蓝牙请求结束并向App返回中断结果；设备展示地址A，交易B未因旧触摸获批或广播 |
| ❗️❗️P0❗️❗️ | 其他设备蓝牙打断USB | 在除Pro2外的适用型号通过USB显示地址A，随后从蓝牙发起交易B | USB请求被中断，设备展示交易B；须重新明确确认才能完成签名 |
| P1 | Pro2蓝牙不能打断USB | 在Pro2通过USB显示地址A，保持USB请求未结束时从蓝牙发起交易B | 地址A请求保持完整，蓝牙请求不替换USB页面，也不获得签名结果 |
| P1 | 处理后两个通道分别重发 | 完成或取消当前请求，分别通过USB、蓝牙重新发起地址核对及测试交易 | 两个通道均可再次交互，返回内容各属本次请求；无旧请求重放、重复签名或触摸锁死 |
