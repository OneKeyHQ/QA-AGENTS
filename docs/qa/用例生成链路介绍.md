# QA 用例生成与 Jira 更新指南

拉取最新代码，在仓库中使用能读取项目规则的 AI，直接描述要生成、补充或修改的用例即可，无需指定 Skill 名称。

```text
根据 <需求链接或文档> 补充 Perps 搜索用例，测试端为 Desktop / Web / Extension，已知 Bug 按修复后的正确预期写。
```

也可以直接引用已有用例文件，说明修改内容。纯手动用例维护无需启动 OneKey 或 CDP；Jira 同步需要当前 AI 可用的 Jira 连接和对应项目权限。若 AI 没有自动加载项目规则，可补充「请按仓库 AGENTS.md 和 docs/qa/qa-rules.md 执行」。

## 生成与更新流程

1. 读取需求、项目规则、相关经验和已有用例，核对最新 app-monorepo 源码；发现需求与实现冲突时核实业务口径，已知 Bug 按修复后的预期写。
2. 补充或修改 Markdown 用例，检查平台范围、遗漏与重复。表格固定四列「优先级 / 场景 / 操作步骤 / 预期结果」，手动用例不增加 ID 列。
3. 同时生成可复制 HTML，核对与 Markdown 一致。复制内容只保留前置条件与用例正文，保留真实换行，不带生成时间、规则来源等说明。
4. 交付后询问是否同步 Jira。用户同意后，有映射就更新对应 Test；没有映射则询问提供编号或确认创建。用户拒绝则结束，不写入 Jira。
5. 同步前核对目标及远端变更，更新后回读校验表格与换行，再更新共享映射和验证记录。若同步失败，如实报告已完成项和阻塞项。

Jira 编号保存在仓库的 [共享映射](jira-test-mapping.json)，不依赖某个 AI 的聊天记忆。默认只更新 Test 的 description；结构化 Xray Steps 和目录操作需要单独支持与授权。生成可复制版不代表已经同步 Jira，离线格式检查也不代表已实测剪贴板。

## 团队共同维护什么

| 内容 | 文件 | 用途 |
|------|------|------|
| 通用格式与优先级 | [qa-rules.md](qa-rules.md) | 统一用例写法与交付格式 |
| 模块产品规则 | `rules/<module>-rules.md` | 维护业务口径、平台差异和边界 |
| 需求 | `requirements/<模块>-<功能>.md` | 记录需求来源、确认结论和变更 |
| 手动用例 | `testcases/cases/<模块>/` | 执行与维护的 Markdown 源文档 |
| Jira 身份对应关系 | [jira-test-mapping.json](jira-test-mapping.json) | 同一个文件对应哪个 Jira Test |
| Jira 同步规则 | [jira-test-sync-rules.md](rules/jira-test-sync-rules.md) | 授权、无映射、并发变更、格式及回读校验 |
| 三线维护闭环 | [qa-workflow-rules.md](rules/qa-workflow-rules.md) | 检查手动、API、UI 自动化之间的影响 |

发现用例口径有误时直接纠正 AI，并确认是否沉淀到对应规范。可选的产品体验建议放在回复中，不混入用例正文或 Jira 描述。只修改手动用例，不代表 API / UI 自动化已经同步或执行通过。

Codex、Claude、Cursor 的入口已接入这套规则；其他 AI 需读取同一套仓库规范。后续计划关联 Kitty，让团队在 Slack 中通过对话维护用例；本次交付包含仓库内流程和 Jira 同步规范，尚未接入 Kitty / Slack。
