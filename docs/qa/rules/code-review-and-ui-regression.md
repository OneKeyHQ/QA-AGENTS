# 代码用例审查与实机回归：两个独立流程

本规范用于 OneKey 模块级代码审查和 UI 自动化回归。2026-11-03 用户明确要求：两个流程分别触发、分别交付；代码中的变化先列建议，经用户确认才维护原有或新增用例。源码用于判断实现，不直接定义业务预期。

## 简单触发口令

| 直接发送 | 路由 | Perps 默认范围 |
|---|---|---|
| `审查 perps` | `onekey-code-case-review` | Desktop 全部适用用例，对比远端最新 x；先报告 bug、差异与用例提案，确认后才维护用例 |
| `回归 perps` | `onekey-ui-regression` | Desktop TF，按最新已确认用例补脚本并执行只读、输入、预览及可恢复本地偏好，独立报告 |

不必记长 skill 名称或输入 `$` / `/`；可换模块名，大小写不敏感，显式平台与范围优先。回归口令仍遵守首次平台选择、本批账户与副作用授权规则；真实交易、远端设置 / 签名、资金操作另行确认。已有确认不重复询问。只要求离线则不连接 App；未指定账户先推进不依赖账户的工作。

本规则为项目内自然语言入口，不安装操作系统命令，也不声称每个客户端都注册了同名原生斜杠命令。仅询问用法、引用口令或维护入口时不实际执行两个流程。

## 入口与边界

| 流程 | 标准 skill | 输入 | 独立产物 | 结束点 |
|---|---|---|---|---|
| A：代码与用例审查 | `$onekey-code-case-review` | 模块 / 平台、当前用例、已确认需求、最新 x 或指定分支，可选历史基线 | 审查报告、缺陷候选、待确认用例变更建议；确认后有单独维护记录 | 报告交付或应用已确认建议；不自动执行 B |
| B：用例驱动的自动化回归与维护 | `$onekey-ui-regression` | 最新已确认用例、目标平台、脚本、本批操作范围；执行时再提供账户 | 用例—断言映射、脚本、实机结果、缺陷 / 阻塞、覆盖率与补测清单 | 完成范围内脚本维护和实机复验；只要求离线时止于离线产物 |

Codex 用 `$skill-name`；Claude / Cursor 对应 `/skill-name`。技能位于 `.agents/skills/`，`.claude/skills/` 与 `.cursor/rules/` 提供同内容入口。自然语言可触发匹配入口；只请求代码审查时不能因为已有自动化脚本而连接 App。`onekey-qa-review` 仍是提交前 QA 规范审查，与 A 的产品行为审查不同。

示例：

```text
$onekey-code-case-review 审查 Perps Desktop 全部用例与最新 x，先给差异、bug 和用例变更建议，不修改用例。
$onekey-ui-regression 基于最新已确认 Perps Desktop 用例补齐脚本，跑 TF 只读、输入与预览回归，交易场景单独排期。
```

## 共同约束：用例变更须确认

代码改动、PR 实现、当前 UI 表现和测试已通过，都不能单独证明需求变更已经确认。已有明确需求与代码冲突时报告缺陷或疑似缺陷；缺少需求依据时报告不确定项，不把实现反写成需求。

本规范中的代码驱动维护在确认前，**只写独立报告和提案**：

- 不修改或新增 `docs/qa/testcases/cases/` 中的用例，也不以“代码推导 / 待产品确认”章节提前入库。
- 不更新用例可复制版、需求正文、业务规则正文或正式自动化业务预期。候选分析 / 最小反例放报告证据区，不进入正式验收覆盖率。
- 提案可以展示完整拟新增 / 拟替换的四列表格、diff 或断言建议，文件名和页面明确“提案，未应用”；不能替换正式用例文件或混进正式可复制版。
- 区分“确认实现事实”“确认是 bug”“确认调整用例”三个决定。用户确认 bug 不代表同意把错误行为变成用例预期。继续审查、执行自动化或提供账户，也不是同意用例变更。

每项建议有独立编号和状态：`proposed / approved / rejected / needs-clarification / applied`。编号仅用于报告追踪，手动用例仍不加 ID。用户可逐项或明确整批确认；确认记录必须能定位消息和具体内容。未确认项继续保留，不阻止其他独立审查和已授权的脚本工作。

应用前比对用例指纹、建议内容和确认范围。内容或相关基线变化时，只重新列出受影响的差异供确认；同一内容已有明确确认时不重复询问。确认后按既有 Test Designer / Knowledge Builder / QA Manager / Runner / Reporter 职责处理，不因流程封装扩大外部写入或交易权限。

## 流程 A：代码与用例审查

### A1 固定输入

读取 QA 格式与模块规范、知识、手动用例和已确认需求。记录用例文件 SHA-256、场景和预期子项、平台适用性。全量请求建立已审 / 未审队列，不以近期改动文件替代整个模块审查。

用远端查询核验目标分支精确 SHA 和时间，读取该 SHA 的源码。记录上次审查 SHA；没有历史基线可审当前问题，但不能称“新引入”。远端无法访问则标“本地缓存快照，最新性未核验”。不切换用户当前分支、不覆盖未提交文件，不从日期推断 TF 包等于某源码版本。

### A2 对照与分析

逐项检查用例的前置、操作、预期与对应调用链：权限 / 平台 / feature gate、校验顺序、状态与持久化、数据与精度、账户隔离、异步响应、异常和恢复。业务规则与代码分别引用，说明差异的可达条件及用户影响。

分类为代码缺陷、疑似缺陷、已确认功能变更、待确认功能变更、用例缺口 / 描述问题、一致或证据不足。结论不能只靠关键字、diff、静态字符串断言或测试退出码；PR 标题也不能单独充当产品确认。高风险发现先报告，不必等全量结束。

可选源码隔离检查须标明固定 SHA、夹具限制、实际 pass / fail / skip / TODO；失败可能来自夹具或版本差异，要区分。它们是分析辅助，不能替代人工调用链审查或记为 TF 通过。

### A3 先交付，再确认维护

默认写入 `shared/reports/<module>-code-case-review-<日期或批次>/`，至少提供 `index.md`、可读 `index.html` 与 `changes.json`。报告按缺陷风险与待确认建议分组，展示代码事实、原有预期、建议内容和理由。确认前正式用例、需求、业务规则和正式断言内容保持原样。

用户明确确认维护后，只更新已确认项，记录修改前后指纹和确认依据。同步交付用例源文件与可复制版并验证一致性，检查 API / UI 断言影响；Jira 同步仍需该批目标的独立授权。未批准项保留。完成后停在 A，不连接 OneKey，也不发起 B。

## 流程 B：用例 → 脚本 → 实机 → 维护

### B1 建立最新用例与断言映射

以当前已确认用例为准，逐条拆出原预期子项，保留文件、章节、场景、行号与指纹。源码用于实现导航和定位，不能代替测试 oracle。待确认代码建议与正式用例分开；既有确认状态不明的条目单列，不删除、不自动从分母剔除。

映射每个预期到自动化 ID、步骤、文件 / 行、断言表达式、数据依据、适用平台和证据层。仅点击、存在文本、非空值、无异常不能自动算覆盖业务预期。跨入口同步须打开目标入口重新读取；动态数值须独立对账，避免同源值自比；清空场景先填数据；样本不足不能空跑记通过。

### B2 补齐脚本并做离线验证

按桌面 / 移动模块契约维护脚本，补齐缺失预期、输入边界和可重复前置。配置与运行时数据不硬编码历史账户。重要操作可追踪，失败和跳过有具体原因，恢复在 finally 中执行并独立读回。

先做适用的语法、定位器构建、辅助断言与反例检查，再实机；离线源码 / 单元证据不计 Desktop UI 覆盖或实机通过。用户仅要求离线时在此交付，列出可执行范围与未验证项，不要求账户、不连接 App。

### B3 执行前按副作用分组

整段脚本审核，分别排只读输入预览、本地偏好、真实订单、账户设置 / 签名、资金操作。本地收藏 / 布局等偏好结束需恢复。账户与交易权限不能互相推定；点击最终提交即使预期拒绝也属于订单批，不混入只读组。

实际执行才确认目标与平台。公开市场场景不要求账户；账户对账使用本批观察地址或钱包名 + 账户名；真实订单、远端设置和资金操作分别提供本批钱包 / 账户及参数。已有本批授权持续有效，暂停后的范围按用户新指令处理。不自动授权、下单或转资金造样本。

Desktop TF 不检查更新，只读取当前安装版本；遵守项目规定的 App 路径、CDP、解锁与窗口规则。不可连接其他浏览器代替目标实例。若仓库已提供 Perps 执行配置，具体队列和前置另读 `docs/qa/automation/Perps-执行分组与账户前置.md`；计划输出不等于实际执行许可或运行时保护。

### B4 执行、诊断、复验

检查网络、页面、权限、样本与弹层；可在当前授权内补齐的前置先补齐再测。无法执行的每个子项记录缺失条件和如何解除，不用笼统“跳过”。通过项目正式入口运行已审核范围，保留当前包版本、运行时间、用例和脚本指纹、各步骤与预期结果、截图 / 日志、恢复读回。

把产品缺陷、脚本 / 断言、环境、缺样本和恢复失败分开。脚本修复后重跑受影响项，保留原失败与新证据，不回填旧通过；业务预期要改则另列提案等确认。产品代码修复另行授权。外部操作干扰、身份异常或恢复失败时停止受影响 UI 队列，继续独立离线工作。

### B5 独立报告与补测清单

写入 `shared/reports/<module>-ui-regression-<日期或批次>/`，交付 `index.md`、`index.html`、逐项断言映射和运行证据索引。单列本批脚本维护、执行缺陷、阻塞原因、恢复结果、仍需实机 / 指定账户 / 真实订单的补测项。代码审查问题可引用 A 编号，另记“已复现 / 本批未复现 / 未执行 / 缺前置”；一次未复现不关闭有条件的源码问题。

## 报告与追踪字段

### A 的问题 / 变更建议

| 字段 | 要求 |
|---|---|
| 建议编号 / 状态 | 可逐项确认；与缺陷编号分开或明确关联 |
| 用例基线 | 文件、章节、场景、原预期、指纹；新增场景写“现有无对应项” |
| 需求依据 | 已确认需求的文件 / 版本 / 消息；无则写“未找到” |
| 代码证据 | 固定 SHA、路径、行号、调用链、可达前置、实际行为 |
| 分类 / 影响 | bug、疑似、变更、缺口等；新引入须附基线和引入提交 |
| 拟修改内容 | 原值 → 新值，或完整新增建议；说明平台与 API / UI 影响 |
| 用户决定 | 确认消息、确认范围、拒绝 / 待澄清；未确认留空 |
| 应用结果 | 实际文件与修改后指纹；未应用明确写明 |

`changes.json` 用对应字段保存结构化条目，不把生成时间、代码 PR 或测试通过替代用户确认记录。无需为了编号修改手动表格格式。

### B 的用例—断言与运行追踪

每行至少包含：用例文件 / 场景 / 指纹、原预期子项、平台、执行队列、自动化 ID / 步骤 / 文件 / 行、oracle、覆盖状态、证据层、本批结果、证据链接、阻塞及解除条件、恢复结果。行号只用于阅读，定位还须依赖内容和指纹。

## 统计口径

先确定单一平台和本次范围，再统计；原始总数、平台不适用项、明确排除项及原因保留。不能通过删除未覆盖项提高比例。

- **代码断言覆盖**：已完整覆盖行 / 当前平台范围内有效用例行。只有前置和全部预期子项都有可追溯、当前有效的目标平台断言才记完整；有部分预期则记部分；无对应断言记未覆盖；未核实记待审核。另列子项覆盖，不以一个 test 函数代替多条用例。源码证据另列，不折算 Desktop UI 覆盖。
- **审核尚未完成**：列已审核数、待审核数、已确认完整数及下界，不能把待审核都当未覆盖或发布最终实际覆盖率。脚本 / 用例变化导致引用失效时重审对应项。
- **实机通过率**：完整通过 /（完整通过 + 失败），同时必须展示通过、失败、部分执行、跳过、阻塞、未执行数量及分母；分母为 0 时写“未执行 / 不适用”。另报完整通过 / 计划范围总数的完成比例，避免大量跳过被隐藏。
- 用例部分步骤跳过、缺预期、缺样本、未恢复或 TODO 都不能记完整通过；即使旧追踪器把 `SKIP:` 写在 passed 的 detail 中，汇总仍按真实未执行处理。源代码测试进程退出 0 也不能覆盖其内部失败。
- 分开记录离线辅助、源码隔离、目标平台实机结果及历史结果，不把旧版本通过迁移到新包；复跑历史可追溯。

## 完成检查

A：基线和范围可追溯、问题有证据、用例变更有逐项建议与确认状态、未确认内容没有入库、不自动启动 B。B：映射逐项有效、离线与实机分开、结果和恢复可追溯、修复有复验或明确未验、补测原因具体。两者都检查手动 / API / UI 三线影响并沉淀到项目文档；没有授权的外部写入不执行。
