# 根据 PR 生成回归项与简短代码审查

## 1. 触发与输出边界

1. 用户给出 PR 并要求「生成回归项」「PR 回归用例」，或在该流程中继续发送单个 PR 链接时，通过 `onekey-test-designer` 的 PR 分支执行。询问流程原理、修改规则时不自动审查历史 PR。
2. 先交付回归用例，再在同一次回复末尾列出全部有依据的「代码审查发现」，包括确认的问题和需验证的风险。先按用户影响排序，同级按证据强度排序。无发现时只写审查结论。
3. 此分支只做本次改动范围的用例设计和代码审查，不自动启动 App、提交交易、修改后台配置、发 Slack、创建 Bug 或写入 Jira Test。单独要求全面审查或实机回归时才进入对应独立流程。
4. 用例文件保持仓库四列格式；代码审查发现作为回复中的独立末尾部分，不塞入正式用例表、需求或业务规则，也不自动同步到 Jira Test。若用户要求文件包含发现，使用独立交付副本或本地报告，正式用例源仍单独维护。详细审查报告按需生成，不默认附大型 HTML / ZIP。
5. Jira 同步询问等交付信息放在「代码审查发现」之前；不因常规同步询问打断本轮生成与审查。

## 2. 输入分别用于什么

| 输入 | 用途 | 不可替代的边界 |
| --- | --- | --- |
| PR 的实际 diff、固定提交源码及相关调用链 | 确定变更、受影响入口、状态与平台；识别潜在回归和代码问题 | PR 标题、描述或单元测试通过不等于已完成代码审查，也不能单独确定业务预期 |
| 用户确认的要求、关联 Jira 需求/验收单、PRD、模块业务规则 | 确定用户操作后应该发生什么 | 需求单不等于 Jira Test；实现与要求冲突时保留要求并报告差异 |
| 仓库现有用例、已映射或与本功能相关的 Jira Test | 复用步骤与数据、找受影响的既有行为、去重和补边界 | 不整份照搬；只纳入能解释其与本 PR 关系的项，不默认跑整个 Jira 合集 |
| 既有代码及修复记录 | 判断改前行为、问题是否由本次改动引入 | 历史问题不默认认定为本 PR 新问题；只在改动触及、仍受影响时说明关系 |

1. 遵循「PR 决定回归范围，已确认需求决定预期，已有用例帮助复用和查漏」。沿改动的调用关系扩展覆盖，不能只按修改文件名选用例。
2. 先查可访问的仓库规则、相关需求和用例；通过映射读取对应 Jira Test，或检索本功能相关 Test，不要求用户重复提供已可查的信息。缺少映射不阻塞生成，也不能凭同名覆盖其他 Test。
3. Jira 不可访问或没有已有 Test 时，注明本轮实际使用的来源和缺口，依据可用需求继续。未读取的 Jira 用例不得声称已对照。
4. 已确认需求与代码冲突时报告问题，不把错误实现写成预期。新行为若只有源码依据，先列独立待确认建议；现有明确要求支持的用例照常输出，不为等待非关键澄清停掉全部交付。
5. 仓库与 Jira Test 版本或口径冲突时，读取当前内容并列出具体差异；不默认 Jira 永远最新。用户已明确确认的本批要求优先，其他不明冲突保持待确认。

## 3. 固定基线与完整性

1. 记录 PR 链接、目标分支、状态及实际比较的起止 SHA。未合并时固定目标分支快照和 PR head，核对 PR 的比较基线（merge-base），按「比较基线 → head」审查。已合并时先确认合并方式，按「目标分支合入前 → 本 PR 最后一个合入提交」核对实际变更。多提交 rebase 必须覆盖整个合入区间。记录原 PR head 与实际合入范围的关系。后续 diff、行号引用及问题归因使用同一对起止提交。
2. 读取全部变更文件列表，处理分页，核对总数、重命名与删除；读取完整可审查 diff，检查缺失 patch、截断与返回上限。必要时读取固定 base/head 源文件或获取完整 git diff。删除内容引用比较起点的行号，其余引用比较终点的实际行号。
3. 对影响行为的变更阅读上下文及实际调用方、hook、service、atom、缓存和平台组件。处理器委托给另一层时继续追踪，不能只从函数名或 PR 描述推断效果。
4. 逐文件记录已读 / 缺失 / 不适用及理由。二进制或生成产物无法用于源码断言时说明其验证边界；配置、原生模块登记也不能当作实际安装通过。
5. 无法核实比较起止提交或实际合入范围、拿不到完整 diff 或缺少必要调用代码时，明确写「审查未完成：缺少……；已检查……」，继续提供有依据的回归项和局部发现，不使用全局“未发现问题”结论。比较范围未核实时，不判定问题是否由本 PR 引入。审查期间 head、比较起点或实际合入范围变化时，重新确认比较范围，并复核受影响的结论。沿用旧结论时标明原起止 SHA。

## 4. 从改动整理回归用例

1. 把改前 / 改后行为与需求逐项对照，找出直接变更、共享调用方及受影响旧流程；复用已有用例，仅补与本次变动有关的主路径、状态切换、边界、异常与恢复。
2. 为每条确定前置数据、真实可操作入口、观察结果和适用端；后台负责的计算与前端展示分开说明，缺失接口字段不等同于业务配置为零。
3. 按 `qa-rules.md` 保留「优先级 / 场景 / 操作步骤 / 预期结果」四列，手动用例不加 ID。等价端与参数合并；代码分支或风险不同才拆开。没有影响的模块不扩展成全量回归。
4. 生成完核对覆盖、去重和用语。把代码发现中的错误行为保留为缺陷依据，回归仍验已确认的正确行为，不把风险猜测当正式断言。
5. 简短注明本轮 PR 基线、已读取的需求与已有用例来源、未覆盖或未执行项；源码审查和离线实验不算实机通过。

## 5. 本次改动的重点审查维度

从变动入口出发，遇到相关代码才深入下列维度。历史数量只用于安排关注顺序，不代表当前 PR 必须命中相同问题。

| 维度 | 必查关系与典型触发 |
| --- | --- |
| 操作描述与执行行为 | 把按钮标签/说明及 i18n key → 当前状态 → onPress/onClick → 实际请求/签名/路由 → 完成后的状态串起来。检查“授权”是否执行授权、“赎回”是否进入赎回、下一步是否跳过确认；多阶段按钮应检查每个状态的文案与动作，不只凭函数名判错。 |
| 权限、签名与提交 | 涉及权限或资金操作时，从确认页追到实际签名、广播或写入入口，核对服务层或服务端执行的权限和作用域校验，确认实际提交的账户、链、资产、金额、授权对象或目标合约与用户确认一致。核对报价是否属于本次操作且仍有效，覆盖切换币种再切回后取价失败。检查连点、重试和超时的去重与状态核对，区分确定未发送和广播结果未知。后者先查原交易，避免重复发送。 |
| 操作状态切换与恢复 | 授权/提交/待处理/取消/失败/完成的状态转换；loading、disabled、待处理订单和去重锁是否释放；退出重进、改选代币、切 Tab/网络/账户后能否继续；旧异步结果是否覆盖新选择、网络选中态是否单一。 |
| 持仓、余额与缓存 | 交易后查询失效与刷新；余额、可赎回数量、法币估值是否来自同一账户/链/资产/协议；不同资产 key 是否碰撞；赎回中/待领取持仓是否被误过滤；区分 0、缺失、加载中和不可用。 |
| 多端与布局渲染 | 追查 .native/.ios/.android/.web 及 Desktop/Extension 分支；真实窗口与布局断点、点击与悬停、弹层和导航、按钮可见性、键盘/安全区、动态高度、空状态/加载态与边框。只查实际受影响端；不把宽度等同于操作系统或假定所有移动端均为底部弹层。 |
| 时间与规则表达 | 等待期从何时算、适用哪类操作；截止时分、时区与转换、单位及边界是否一致；本地时钟跨截止后是否重算；无产品要求时不凭偏好认定文案必须包含某字段。 |
| 异常处理与提示 | 请求/签名失败、超时、取消是否清理状态并保留可恢复入口；业务错误是否被吞成笼统“服务器错误”；不可操作时能否从现有需求确定应显示的原因或指引。 |
| 多语言与数字格式 | 文案 key/占位符与当前语言是否匹配；金额、千分位、小数分隔符、日期是否使用当前 locale；切语言后 formatter/memo/缓存是否更新；展示格式不应反向破坏提交金额解析。 |

## 6. 发现的证据与级别

1. **确认的问题**：已有明确需求、行为契约或可证明的逻辑不变量；所读完整调用链能给出可达触发条件与具体错误结果。静态可证明时无需伪造实机复现，注明“静态确认”或实际实验方式。
2. **需验证的风险**：有具体代码路径和条件，但还缺真实接口形态、平台表现、竞态时序或产品口径。写出缺什么及最小验证动作，不能把泛泛担忧列成发现。
3. 对照改前代码检查因果。区分本 PR 新引入、改动暴露的既有问题、未能确定引入时间。已在所审提交修复、与本次范围无关或仅涉及格式和风格的条目不列为发现。
4. 严重程度按用户影响：P0 为可达的资金损失/越权或广泛核心功能阻断；P1 为核心操作或关键资产信息错误、特定条件阻断；P2 为局部展示/提示/适配错误。严重程度与确认状态分别标注，风险不因未实测自动降级，也不因涉及钱包自动标 P0。
5. 每条必须含：确认状态、严重程度、固定 SHA 下的文件/行号（可点击源码链接）、触发条件、影响。风险另加一句缺失证据或最小验证方式；跨文件因果只保留关键位置。
6. 列出全部有足够依据的发现，按用户影响从高到低排序，同级按证据强度排序。有具体证据的高影响风险可排在已确认的低影响问题前，仍标为「需验证的风险」并给出最小验证动作。同根因的重复现象可以合并，保留各触发条件和影响。代码路径猜测、测试缺失本身或 PR 的自述测试结果不足以作为缺陷证据。

## 7. 回复末尾格式

先给四列回归用例或文件链接、来源与必要交付信息，再追加以下独立部分；只展示实际存在的发现，不生成空表凑数。

```markdown
## 代码审查发现
审查 <PR 链接> 的 <比较起点 SHA> → <比较终点 SHA>，覆盖 <本次 diff 与必要调用链>。

- **[确认的问题][P1] <一句话问题>** — <文件:行号源码链接>。触发条件：……。影响：……。证据：静态确认 / 已执行的源码实验。
- **[需验证的风险][P2] <一句话风险>** — <文件:行号源码链接>。触发条件：……。影响：……。待验证：……。
```

1. 完整审查且无发现时，只写 **「未发现明确代码问题」**，省略发现条目。只有待验证风险时列出风险并注明确认状态。
2. 审查不完整时，写 **「审查未完成：<未核实的比较范围或缺失的 diff / 源码及其影响>」**，列出已读范围内有证据的发现；不能使用上述无问题结论。
3. 区分静态审查、源码实验、现有测试阅读与实际测试执行；未跑的平台不写通过。代码审查摘要也不等于已经提交 Jira Bug。
