## 1. 凭证与添加反馈

1. 传统U2F在网站核对绑定和登录，不以设备驻留凭证列表新增作为通过条件。
2. FIDO2明确保存驻留凭证到设备后，显示“安全密钥已添加”Toast，列表记录与本次网站、用户名对应。新增数量场景使用不同用户名，避免同用户替换已有凭证混淆新增。
3. 批准或写入前取消、断连、超时不新增列表记录、不显示添加Toast；重新发起并保存后仅反馈本次完成的添加。
4. 使用已有凭证仅认证时不显示添加Toast，列表数量不变；没有新添加操作时，退出重入不重放旧Toast。
5. 使用USB安全密钥/WebAuthn通道验证浏览器，不把WebUSB权限当作协议前置。锁定时先解锁，再确认请求。

## 2. 旧场景维护

1. 保留升级后原U2F绑定可验证、驻留凭证保留、取消重发，以及超时、断连、锁定、关闭网站和并发请求隔离。
2. 传统递增U2F样本保留Google/Binance计数器差异、相同测试种子双设备、重置及诊断/修复。站点策略来自既有样本，固件源码不能证明第三方当前策略，执行时需使用已核实的专用测试样本。
3. trezorctl fido counter get-next会自增，不能当作被动读取；只在专用诊断环境操作。修复只保留一条同步高于已知阈值后再认证的闭环，不重复列相同结果。
4. 不将所有FIDO2计数器统一断言每次加1；有零计数器分支。没有真实站点日志时不要求直接读取不可见的服务器计数器。

## 3. 范围与安全

本次用例为USB注册、验证与添加提示；NFC和完整列表/开关管理有各自独立用例，不由OK-54499整份替代。升级、重置及计数器设值使用已备份专用测试设备，文档不填写凭证或助记词。本轮只做离线用例review，不代表设备或第三方站点实测通过。
